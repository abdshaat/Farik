Plan for CTV-9: no sprints, clear escalations, stuck agents move on, and a UX walkthrough

Written by Ada, the Architect, for task CTV-12. It splits the approved epic CTV-9 into nine tasks in two lanes: lane 1 for Theo, the Software Developer, and lane 2 for Iris, the UI/UX Designer. A builder who has read their task here and the rules below knows what to build and where to stop.

Short version: sprints leave the product. In their place a delivery closes when an epic is accepted, when five standalone tasks have been accepted, or when the team runs out of work. Each delivery runs the review, the plan refresh, the changelog and the retro the sprint used to run. A blocked, escalated or waiting task stops counting towards its agent's WIP limit. When it clears, it goes back to that agent if they have room, else to the first free agent of its role. A decision that supersedes ADR 0028 records all this.

3. The trigger that replaces the sprint ceremonies (R3)

The trigger is a delivery. Catervas closes one, as the governor, in a tick scoped to no task under the All rules, the first time one of these holds since the previous delivery closed:

  1. An epic is accepted.
  2. Five standalone tasks (tasks with no parent) have been accepted. The count is a constant, TASKS_PER_DELIVERY = 5, not a setting.
  3. The team runs out of work. At least one task was accepted, and no task is left in ready, assigned, in_progress, verifying or rejected. Blocked, escalated, draft and refining tasks do not hold a delivery open.

A delivery holds every task accepted since the previous one closed. It is recorded as a new event, delivery.closed, with delivery_id D<n>, trigger (epic_accepted, tasks_accepted or team_quiet) and task_ids. Each closed delivery then gets, once and in this order, what an ended sprint got:

  • The review, run by the assigner (the active Scrum Master, else the Product Manager). It is told each task's status, cost and completion note, what the delivery spent, and the digest of open escalations (ceremonies::open_escalations with the Digest the planning ceremony used to get).
  • The Product Manager's refresh: its proposed changes to the spec and roadmap, and its report at docs/catervas/product/reports/D<n>. After it, the Architect's refresh, both under today's due_refresh rules.
  • The CHANGELOG entry. Catervas itself files a small docs task for the Product Manager, "Changelog for D<n>", with allowed_paths: [CHANGELOG.md], so it flows through refining and assignment like any request. Today the Product Manager's prompt asks it to file this task at each sprint review, but no ceremony session is offered catervas_create_task (CEREMONY_TOOLS in crates/runtime/src/orchestrator/rules.rs), so it never could. A deterministic filing is the only way it happens "with no action from the user".
  • The retro, run by the assigner, offered catervas_append_retro.

Why this trigger. An epic is the unit the owner approved, so its acceptance is the natural moment for a changelog line and a plan refresh. Standalone work has no such moment. Five tasks keep a changelog entry readable and keep the review, refresh and retro sessions, which are paid, from running after every small task. The quiet rule makes sure a small project's last work still gets its changelog and retro. None of the three asks the user for anything.

Ruled out. A timer, such as weekly, would close empty deliveries and is a sprint by another name. A delivery after every accepted task would cost a review, a refresh and a retro per task. A "close delivery" button would bring back the user action that question 34 removed. The daily standup is dropped without a replacement: the digest moves into the review, and the existing aged-escalation rule (aged, escalation.aged) keeps reminding about old escalations.

The decision. Task 1.1 records this in a new decision, docs/decisions/0061-deliveries-replace-sprints.md (or the next free number when it lands), whose header says Supersedes ADR 0028.

4. How old projects keep working (R2)

  • team.yaml. policy.plan_in_sprints (true or false) stays in docs/schemas/team.schema.json as an accepted key that nothing reads. Its description says it is read from projects made before the new decision and ignored. Team::plans_in_sprints (crates/core/src/team.rs) is deleted. When Catervas next writes team.yaml, it leaves the key out. policy.ambient_messages_per_sprint becomes ambient_messages_per_day, and the old key is read as its value when the new one is absent. The period was already a UTC day whenever no sprint was open.
  • Team templates. plan_in_sprints leaves docs/schemas/team-template.schema.json (epic C3). crates/core/src/team/template.rs drops the key from a saved template before validating it, so a template a user saved earlier still loads.
  • Contracts. The optional sprint field stays in task-contract.schema.json, read and ignored. Catervas never writes it again.
  • Sprint files. .catervas/sprints/* are left where they are. Nothing reads them, writes them or deletes them.
  • Sprint events. sprint.started, sprint.planned, sprint.ended (with its backlog mark and left tasks) and ceremony sessions in the planning and standup threads stay in docs/schemas/event.schema.json and in catervas-protocol's event kinds and threads, so an old log parses. The store may go on applying them to its sprint tables (migrations 0008 to 0010 and 0015 stay; a migration is never removed). No rule, gate, query or page reads them. The one exception is the first delivery's starting point, below.
  • The Backlog hold. waits_for_a_sprint, in_the_backlog, in_the_open_sprint, the_sprint_pays and SprintHold (crates/core/src/governor/gates.rs) are deleted, along with sprint_hold and backlog (crates/runtime/src/sprints.rs) and the goes_on filter in tick. A ready task that sat in the Backlog is then assigned by rule 8 on the first tick, like any ready task. A task carrying the left_for_the_backlog mark in assigned, in_progress or rejected is started, worked or reworked by rules 7, 6 and 3. The projection's column stays and is not read.
  • An open sprint at upgrade. It is never ended. Catervas appends no sprint event, ever again. Its tasks are ordinary tasks.
  • The first delivery counts tasks accepted after the later of the last delivery.closed and the last sprint.ended whose review ran. Work an old sprint already reviewed is not reviewed twice, and work accepted after it is not lost.
  • Past events are neither rewritten nor deleted. No task in this plan edits or removes a line of any project's log. This repository's own .catervas/team.yaml is not edited by hand: its leftover key is simply ignored.

5. WIP counting and assignment (R5)

The counting function is transitions::open_tasks in crates/runtime/src/transitions.rs. The orchestrator's has_room (crates/runtime/src/orchestrator/rules.rs) and the governor's AssignmentInput::assignee_open_tasks both read it. After 1.5 it counts the tasks an agent holds in assigned, in_progress, verifying and rejected, except a row whose waiting_on_human is set. It leaves out blocked, escalated, accepted and cancelled, and it takes no sprint argument. Counting assigned, verifying and rejected keeps the reason given in AssignmentInput's comment: the limit cannot be walked through them.

The resume rule. When a wait clears, the task counts again. The clearing moves are blocked → in_progress, a resolve out of escalated into assigned, in_progress or rejected, and an answered question. A new function, within_limit, takes the place of goes_on in tick. It ranks an agent's counted tasks by when each last became counted, and rules 7, 6 and 3 work only the first wip_limit_per_agent of them. A task past that rank is returning, and a new rule between rules 5 and 6, resume, does this with it:

  1. If its previous assignee has room again, it simply goes on with them on a later tick, because it is now within their limit.
  2. Otherwise, the first active agent of its assignee_role, in team order, that has room and is not the task's reviewer, gets it. The governor appends a new event, task.reassigned (from, to, reason: resumed), under a new gate, check_reassignment, in crates/core/src/governor/gates.rs. The projection sets assignee_id from it. The task keeps its worktree and branch, and its next session is told the last commit and note, as resume already does.
  3. If no agent has room, it waits with its previous assignee and is tried again every tick.
  4. A task with a lane is never handed over. It waits for its lane's builder, so two agents never work in one lane's paths at once (ADR 0051, lanes_overlap).

Why no task is held by two agents. A task has one holder, the projection's single assignee_id. Only two events set it: ready → assigned, behind check_assignment, and task.reassigned, behind check_reassignment. check_reassignment refuses unless the task is in assigned, in_progress or rejected, is returning, has no lane, and the candidate has room and holds the task's role. One process drives a project (ADR 0053), its tick runs one rule at a time, and a session runs to its end before the next tick. So no reassignment can land while the task's session runs. Rules 3, 6 and 7 start sessions only for the row's current assignee_id.

Why nobody reviews their own work. The reviewer is fixed at assignment and task.reassigned does not change it. check_reassignment refuses a candidate who is the task's reviewer_id, with the same exception check_assignment makes for Role::reviews_its_own (the Product Manager alone). The previous assignee could not be the reviewer either, since check_assignment refused that when the task was first assigned.

6. Escalation choices (R4)

escalation.choices (choices in crates/runtime/src/daemon/gates.rs) gains, for each choice, next (what happens next, in plain words, naming the agent), suggested (exactly one per escalation) and kind (command, or open with a path for a choice made on another page). It covers every reason in escalation.raised; today four reasons get no choice at all. No two choices send the same command. The shape below is fixed, and Theo may improve the wording:

ReasonChoices, suggested firstExample of next for the suggested one
iterationsGive 2 more tries; ask the Product Manager to change the plan; cancel"Theo picks CTV-14 up again with 2 more tries."
budget, sessionsAsk the Product Manager to change the plan; cancel"Mira rewrites the plan of CTV-14; it is assigned again once it is ready."
blocker_ageAnswer the blocker and carry on (to in_progress, the message being the answer); change the plan; cancel"Theo reads your answer and carries on with CTV-14."
permission, explicit_requestCarry on (to the status before); change the plan; cancel"CTV-14 goes back to in progress, and Theo is told what you wrote."
readiness_failuresAsk the Product Manager to try the plan again (to refining); cancel"Mira writes the plan of CTV-14 again with your note."
approval, risk_gateReview the plan (open the approval); cancel"You read the plan and approve it or send it back."
integrationAdd it to the project now (the integrate command); cancel"Catervas merges CTV-14 into your main branch."
previewSet the preview (open Settings); cancel"You tell Catervas how to start your app, and Iris carries on."

Cancelling always says: "CTV-14 stops for good. Its branch is kept, and nothing is merged."

7. Rules for every task

  • Follow ADR 0060: write one test for each major functionality first and watch it fail for the right reason. Do not add one test per case.
  • Leave pnpm run check and cargo xtask check passing at the end of every task. Where an epic criterion is a test, leave cargo xtask check --integration passing too.
  • Rewrite or delete no past event in any project's log. Never edit this repository's .catervas/ by hand.
  • Take on no new dependency.
  • Write new documents under docs/catervas/ as HTML (ADR 0058).
  • Change only what the epic's scope names. The WIP limit's value, the escalation reasons, their limits, the budgets, milestones beyond their sprint words, and the desktop app stay as they are.
  • Iris's tasks run as the Designer's do: explore, then a plan the Product Manager approves, then the implementation.
