# 0069. The open issues of the note-chat2 journey

Date: 2026-10-17
Status: accepted (the founder, 2026-10-17: "fix the open issues in Catervas, especially the governor escalation"; every mechanism below decided by the planner the same day, as the founder asked not to be asked)

Amends:
- **SPEC 5.2**'s transition table: three rows into and out of `blocked`, one out of `accepted`, and `blocked -> in_progress` opening only for a block that came from the work (decisions 1 and 4).
- **ADR 0068** item 2: a blocked task's choices go back where the block came from and offer "Ask {pm} to change the plan"; the tidy runs before each work session too (decisions 2 and 7).
- **ADR 0062**'s choices: the same, for a `blocker_age` escalation (decision 2).
- **ADR 0066**: a delivery's report is titled by its name alone (decision 10), and a pull request's body is two short sections (decision 11).
- **ADR 0004** and **SPEC 8.3**: the containers that run a task's checks see the repository's git store, read-only (decision 6).

## Context

The journey on note-chat2 (2026-10-17, `reports/note-chat2-journey-2026-10-17.html`) left fourteen issues open; the founder added a fifteenth after reading its pull requests. The log (`~/note-chat2/.catervas/local/catervas.db`) shows the worst one exactly:

- Ada, the reviewer, asked for `verifying -> blocked` on CTV-14 (seq 3242), CTV-24 (5285) and CTV-25 (6169). `catervas_declare_blocked` asks as the assignee whoever calls it, and no row leaves `verifying` for `blocked`, so each was refused `no_such_transition`. She asked the owner questions instead ("run these four git commands", "look at this page at 375 and 1024 px").
- Then rule 5 froze all three: it passes over a `verifying` task with any `transition.refused` since it entered `verifying`. The owner answered CTV-14's question at seq 4458 and no session ever followed; the three were still `verifying` at the end.
- CTV-7, a bug hunt that wrote one HTML report under `docs/catervas/`, was frozen the same way (seq 1529): `**/*.html` is a UI path, so the governor's own acceptance waited for a design review that a document never gets, and the refusal parked it with nobody told.
- 31 of the 41 refusals are the governor's own probe of `refining -> escalated` before `refining -> ready` on every passing contract: no dead end, but noise that hides the real ones.

## Decision

1. **Whoever holds a task and cannot finish it blocks it, and the owner answers it where it stands.** The holder is the assignee in `assigned` and `in_progress`, the reviewer in `verifying`, and the Product Manager (or the agent the task was given in its chat) in `refining`. `catervas_declare_blocked` asks as the caller's actor on the task (the rows' first actor it is, as `catervas_request_transition` does). New rows: `verifying -> blocked` (reviewer, a written blocker), `refining -> blocked` (Product Manager, a written blocker), `blocked -> verifying` (Scrum Master or human, a written resolution) and `blocked -> refining` (human, a written resolution). The governor reads where the block came from (`blocked_from`, the `from` of the last move into `blocked`): `blocked -> verifying` opens only for a block from `verifying`, `blocked -> in_progress` only for one from `assigned` or `in_progress` (or with no record, for older logs), and `blocked -> refining` for any. Nothing else moves; `rejected` and `ready` have no holder (the governor moves `rejected` at once, and a `ready` task waits for an assigner), and the UI/UX Designer's design review is a check, not a held task: a page it cannot judge it fails with its reason, and a preview that will not start is escalated by Catervas (`preview`).
2. **The blocked row's choices fit who is stuck.** "Waiting on you" names the agent that blocked (the blocking move's agent), not the assignee. "Answer and carry on" goes back where the block came from: the reviewer finishes its review, the Product Manager its contract, the assignee its work. "Ask {pm} to change the plan" (to `refining`, the refine session told the blocker's words) follows it whenever the block did not come from `refining`, so a contract too narrow for its fix (CTV-22) is widened in one press. "Cancel the task" is last. A `blocker_age` escalation of a blocked task offers the same three. The owner's words reach the next session of whoever is stuck through `escalation.resolved`, as now: `human_message` shows it to every session but a reviewer's of its own task.
3. **A refusal no longer parks a task.** Rule 5 passes over a `verifying` task only for a refusal of the governor's own since it entered `verifying`; an agent's refused request is shown to the reviewer's next session ("Catervas refused your last request: …"), whose budgets bound the retries. When the governor's own acceptance or rejection of a task it verifies alone is refused, Catervas escalates the task with the refusal's words instead of passing it over. A team's documents (`docs/catervas/**`) are never a UI change, whatever their extension. The governor judges a contract by asking `refining -> ready` first and `refining -> escalated` only when that is refused, so a passing contract records no refusal.
4. **A pull request that stops merging goes back to its author.** Rule 2's poll reads `gh pr view --json state,mergeCommit,mergeable`. On `CONFLICTING`, for a task: Catervas fast-forwards the integration branch from `origin`, adds the task's worktree again on its kept branch, and merges the integration branch into it on the host. A clean merge is pushed (the same pull request updates), the worktree removed, and `pull_request.refreshed { url, sha }` recorded. A conflicted merge is left in the worktree with its markers, `pull_request.conflicted { url, into, paths }` is recorded, and the governor moves the task `accepted -> assigned` (new gate `pull_request_conflicted`), the one row that leaves a terminal status; rule 7 finds the worktree there and starts the assignee, whose implement message lists the conflicted files. The agent resolves them inside its paths, or blocks the task when one lies outside them; `catervas_git_commit` refuses a file that still holds conflict markers and, the merge being in progress, its commit is the merge commit. The task is reviewed and accepted again, and rule 2 pushes the branch, which `open_pull_request` finds open and reuses. `UNKNOWN` (GitHub computes it after a push) waits for the next tick. A folder change that stops merging is escalated once, as a closed one is. A delivery counts a task once, however often it is accepted. Rejected: filing a new task for the rework (a second worktree cannot hold the same branch, and the review history would split); leaving it to the owner on GitHub (the founder's "goes unnoticed").
5. **A reviewer's browser question is the Designer's, and is already answered.** The reviewer's brief carries the Designer's latest design review since the task entered `verifying` (its checks, widths and themes, and violations), and the Verify instruction says how a page looks and behaves in a browser is the UI/UX Designer's check, shown there, and is never asked of the owner. Rejected: giving the Architect the preview and the browser (a second preview per task, the Designer-only connector rule in the kit loader, and the page check's role rule, for a check that already ran).
6. **The checks see git, read-only, unless the repository's settings hold a password.** Catervas's `command` and `test` criteria run in a container that mounts the worktree's git store (`git rev-parse --git-common-dir`) read-only at its own absolute path, so the worktree's `.git` file resolves. The container is made for the checks and dropped after them, so no agent session ever has the mount (ADR 0004: agents use `catervas_git_*`). Read-only, git in a check can read and never write: no hook, no `core.fsmonitor`, no ref can be planted for the host's next git. Because every sandbox has the network (ADR 0061), a store whose config holds a secret (a remote URL with a user part, or any `http.*.extraheader`) is not mounted, and its checks run without git, as before. The base container of a `new tests` criterion is unchanged.
7. **Tidy before each work session too.** The ADR 0068 tidy runs before every implement session of a task with a worktree, as well as before the move into `verifying`, and never while a merge is in progress in the worktree (decision 4 leaves one there on purpose).
8. **Small fixes, decided:** setup's spending example reads as an example ("Say the team spends $128.00 in a day: $72.00 of $200.00 is left."); a project with a tracked `package.json` and no tracked lockfile is an npm project, and `bun.lock` is Bun's; Settings → How work runs sets the integration branch, saved only when a local branch of that name exists; `/chats` and `/chats/:id` open the chats (`/channel` stays their place); an agent added to a saved team gets its role's persona, and a UI/UX Designer the built-in browser, unless the owner gave them; the server's credential line names the private file honestly; the two end-to-end serving tests run with their own settings folder and no keychain; stale words since ADRs 0061 and 0063 are rewritten (plan 7 lists every key).
9. **Not in this bundle:** the product plan's and a Catervafication's need for an Architect or a Scrum Master (a behaviour of its own; its refusal words become plain), task ids in file names and document text (ADR 0066's known gap), judging a "suite passes" criterion against the base's own failures, and the visual redesign (planned on its own branch).
10. **A delivery's report is titled by its name.** `docs/catervas/product/reports/D<n>` is named "Report for delivery <n>" on Today, in its branch and in its pull request, which is titled "Docs: Report for delivery <n>"; every other folder change keeps "Docs: Update <names>".
11. **A pull request's body is short** (the founder, 2026-10-17: "The PR description must be short, describing the feature or fix, and how they verified the fix or that the feature works"; note-chat2's PR #26 was about 8 KB of notes). Catervas composes it itself, with no session, in exactly two sections: "## What changed", the contract's `summary` (else its title), at most three sentences and 600 characters; and "## How it was verified", one line per exit criterion by its text (the task is accepted, so each passed) and, for a reviewed task, "Reviewed by {name}: {the first sentence of the review note}", at most 200 characters. No intent, no completion note, no evidence, no task id (ADR 0066). The body is at most 1500 characters: past it, criterion lines are dropped from the end and "- and {n} more checks" closes the list. A folder change's body lists its documents and says how it was checked (written at the delivery's review, documents not being reviewed, ADR 0061; or approved by the owner); the changelog task's is a task's. Rejected: an agent writing the description (a session per pull request, and the founder's complaint was agents' text); keeping the notes behind a fold (still metadata dumped on the reader).

## Consequences

- Every agent that holds a task has one legal move that reaches the owner, and every choice the owner is shown is a move the governor allows from where the task stands.
- Two event kinds are added, `pull_request.conflicted` and `pull_request.refreshed`, 122 in all; one gate, `pull_request_conflicted`.
- `accepted` stays terminal for every other purpose (WIP, cleanup, dependents counting it), and a dependent that started from its branch keeps what it had.
- A reviewer's block re-enters `verifying` on its answer: Catervas runs its checks again and the Designer looks again. The second look is the price of one rule for every re-entry.
- A repository whose remote URL carries a token gets no git in its checks until the token moves to a credential helper.
