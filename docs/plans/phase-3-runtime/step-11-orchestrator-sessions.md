## Goal

Farik runs agent sessions on its own and takes a standalone task from `ready` to `verifying`: the Product Manager (or the Scrum Master) assigns it in a `plan` session, the orchestrator gives it a worktree and starts it, and the assignee's `implement` sessions run until it asks for `verifying`. Every session is started, costed, and closed the same way, and a budget that has run out ends the running session and starts no more until it has room again. Tested with recorded sessions that really call Farik's tools. Out of scope: `verifying`, `rejected`, `blocked`, and acceptance (step 12); integration, cleanup, and recovery (step 13); triage, refining, epics, questions, and the human's commands (step 14); the command line (step 15).

## Decisions

- One `Orchestrator` in `farik-runtime::orchestrator`. `tick` finds the first thing on the board that needs doing, does it (running at most one session to its end), and says what it did; `run_until_idle` ticks until a tick is idle or `stop` was called; `stop` sets a flag read before each tick and does not abort a running session (the user's stop that does is step 14's `SessionStop`). Sessions run one at a time, which is what makes a run replayable in a test and needs no "is a session running" check anywhere. Marked `ponytail: one session at a time, a session pool when a team outgrows a WIP limit of one`. Chose this over a session per agent in parallel, which Milestone 0's three agents do not need.
- The order a tick looks in, one rule per state, the first match winning and ties going to the lower number in the task id: (1) `accepted` or `cancelled` with a worktree left (cleanup, step 13); (2) `accepted` awaiting integration under `auto_merge` or `pull_request` (step 13: a merge and push, or opening and then checking a pull request); (3) `rejected` (step 12); (4) `blocked` past `blocked_limit_hours` (step 12); (5) `verifying` (step 12); (6) `in_progress`; (7) `assigned`; (8) `ready`. Chose governor-only moves before sessions because they cost nothing, and work nearest to `accepted` before new work so that a WIP slot frees before it is asked for. States with no rule, on purpose: `draft` and `refining` (step 14's triage and refining), `escalated` (the human's), `blocked` under its limit (the Scrum Master's or the human's), `accepted` under `manual`, or with an integration escalation since its acceptance (the human's), `cancelled` with nothing left. This step writes rules 6 to 8; steps 12 and 13 add theirs at the places named here. The two idle reports are exactly `Idle { why: "nothing on the board needs doing" }` and, when the day's budget is spent and no rule that starts no session matched, `Idle { why: "the team's daily budget is spent" }`.
- `ready` (rule 8), for a task with `kind: task` and no `parent` (an epic's children are assigned by its breakdown, step 14): the assigner is the active Scrum Master, else the Product Manager (D6), in a `plan` session whose task is that one. It starts only when the team has an active agent of the contract's `assignee_role` whose open tasks on the board (neither `accepted` nor `cancelled`) are below `wip_limit_per_agent`; and only when every dependency is `accepted` and integrated as `Transitions::context` reads them (the `dependencies` of its `assignment` for the `ready → assigned` request, so that step 13's widening of `integrated` reaches this check with no second change; until then a task with a dependency waits, which is what step 04's context says). Otherwise no rule, because a session that can only be refused spends a session of the task's for nothing. Rejected: letting the session try and be refused.
- `assigned` (rule 7): the worktree `.farik/local/worktrees/<id>` on `farik/<id>` from the integration branch (`policy.integration_branch`, else `Git::default_branch`), reused when it already exists; then `assigned → in_progress` asked through `Transitions::request` as `Assignee` with the assignee's id, so `requested_by` is the assignee, which 5.2's "assignee starts session" allows. No session in this rule: the next tick's `in_progress` rule starts it.
- `in_progress` (rule 6): the assignee's `implement` session. Its sandbox comes from the private `Orchestrator::sandbox_for(task_id, team) -> Result<Arc<dyn Sandbox>, OrchestratorError>` over `sandboxes: Mutex<BTreeMap<TaskId, Arc<dyn Sandbox>>>`, which creates it on first need in this process with the factory with the network on when the assignee holds `network`. Chose lazy creation over creating at assignment, because it is the same code after a restart (step 13) and a container for a task nobody is working on is a container for nothing. Its first message names the task and, when the branch has a commit past the base or a note was written since the last move into `in_progress`, adds `Resuming: last commit <sha> <subject>; last note (<kind>): <text>`, the note inside step 10's `untrusted_block` (and the subject inside one of its own, `commit_subject`: changed 2026-09-23 by the final review, because the assignee wrote the subject). An implement session that ends without a transition leaves the task `in_progress`, and the next tick starts another: `max_sessions` is what bounds that loop, the task being passed over once it is reached.
- Session mechanics, the same for every purpose, in `orchestrator/session.rs`: the id from `IdSource::session_id`; the role from `load_role`, the model and effort the agent's own `model` in the team when set, else the role's; the prompt from `assemble_system_prompt` with the scan (`read_project_scan`, absent when unreadable as missing), the agent's memory (`read_memory`), the team's rules, the library, the contract, `tool_descriptors()`, the built-ins, the purpose, and `human_message: None` (step 14 fills it); `builtin_tools` from `allowed_builtins` over the agent's tiers; `farik_tools` the names of the Farik tools those tiers allow; `mcp_servers` empty (step 08 adds Farik's own); `limits` from `budget_state`; the prices from `files.effective_prices()` read per session; the team from `read_team()` read at the start of every tick. `cwd` is the project root for a `plan` session and the task's worktree for an `implement` one. Order: `register_session` (with the executor for `implement`, none for `plan`), `record_session_started`, `start_session`, then events are read until `Ended`. A start that fails records a zero-usage `cost.recorded` (below), `session.ended { reason: error }` with the adapter's words, ends the registration, and the tick returns `Err(OrchestratorError::Runtime)`, because an adapter that cannot start sessions is not something the next tick would do better.
- While reading: `UsageReported` is costed with `record_session_cost` (the `CostSource` carrying the session, the agent, and the task, for every session about a task, `plan` included), `budget_state` read before and after with a `SessionLedger` of the usage so far, `DaemonState::tool_calls`, and the clock's time since the start; then `record_exhaustion`. `Ended`: `record_session_ended`, `end_session`. A channel that closes without `Ended` is ended `error` with "the session's events stopped without an end". A session that ends, or fails to start, without any `UsageReported` gets one `record_session_cost` with `Usage::default()`, so that the cost projection counts it as a session and `max_sessions` bounds a run of crashing sessions too.
- Budgets, kept minimal on the founder's word (2026-09-22: "we can enhance budget tracking later"): every session's usage is recorded with step 03's functions, and when `record_exhaustion` reports a scope other than `TaskSessions` the running session is aborted if it is still running. `TaskSessions` is not among them: it crosses at the usage of the last session the task is allowed, which is a session to finish rather than to cut, so it is read only before a start. Before starting any session, `check_budgets` over `budget_state` with an empty ledger is read: a `DayUsd` exhaustion starts no session at all (the governor's own moves and every rule that starts no session, rule 7 included, still run, because they spend nothing; the tick is otherwise `Idle` with the daily budget's words); a `TaskUsd` or `TaskSessions` exhaustion starts none for that task, so the rule passes it over and the next task is looked at; a session-scope exhaustion needs nothing, because the next session starts with an empty ledger. Nothing is escalated and no note is written for a budget. 5.5 gains one sentence naming this phase's minimum and saying the rest arrives in phase 4; its fuller consequences (a session-exhausted task blocked with a note, `escalated` on its dollars or its sessions) are deferred to phase 4, whose sprints step 02 already reworks `budget_state`, and the project plan's phase 4 section already carries that open item. Rejected: this step's first draft, which escalated through the governor's `any → escalated` and wrote a governor's progress note, because the founder put budgets out of focus and the minimal version cannot loop: a task that runs out simply waits. `StopNewAssignments` has no effect in phase 3, where the sprint is unbounded (revision 8).
- Every session about a task carries that task's id in its `CostSource`, the `plan` session included, so that `max_sessions` bounds every loop above (a plan session that does not assign, an implement session that stops early): a task past it is passed over. A clean task takes four sessions (plan, implement, review, accept) against the default of 5; whether the default should rise, or the plan session stop counting, is phase 4's with the rest of the budgets. Rejected: leaving the plan session's cost on no task, which leaves a Product Manager that never assigns bounded only by the day.
- Out of scope, and why: escalation on a denied permission (`TransitionAsk::permission_denied`), because nothing in phase 3 knows which actions a task requires; the Scrum Master's judgment review, because no Scrum Master ships until phase 4.
- Recorded sessions call Farik's tools: `RecordedAdapter::with_tools(transcripts, runner)`. Without tools the adapter is as step 01 left it. With them, replay runs in a spawned `tokio` task (so `start_session` must be called inside a runtime) that sends each event in order; after sending a `ToolCalled` whose tool starts `mcp__farik__` it awaits `runner(session_id, tool, input)` and puts the answer's compact JSON in place of the output of the next `ToolReturned` naming that tool.
