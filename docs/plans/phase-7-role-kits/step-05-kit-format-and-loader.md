## Goal

Each role ships a kit, `roles/<role>/kit.yaml`, beside its `role.yaml`: the skills it carries and the services it may be connected to, each with the setup copy the user reads, its keys or its sign-in, and every tool already labelled. When this step is done, Farik loads the kit with the role, a kit's skills load into the role's sessions on demand, the UI/UX Designer's built-in browser is defined in its kit, and the user connects a kit's service to an agent by name, on the agent page or with `farik connect <agent> <name>`, typing a key or signing in and labelling nothing. A test pins every shipped connector's tool list. Out of scope: allowances on spending tools, their count, the board's and the Costs page's lines and `ConnectorAllowance` (step 05b, split from this row at its seam, which consumes this step's `allowances` in the kit); the contents of any kit but the Designer's browser (steps 06 to 12); the team builder's "Connect" steps at setup.

## Decisions

- **The split.** Row 05 is two plans: this one (the kit file, its loader, kit skills in sessions, kit connectors connected by name, the pins), and 05b (allowances end to end). The mockups of both are drawn in this step's Task 1, so the founder approves the connector screens once.
- **The kit file.** `docs/schemas/kit.schema.json` (JSON Schema 2020-12) holds `role` (the role ids of `role.schema.json`), `skills` (names, at most 20, unique) and `connectors` (at most 20). Its types are generated by `typify::import_types!` in `farik_roles::generated::kit` (ADR 0009); `farik-roles` owns the schema and reads the file with `serde-saphyr` under `yaml_options` (ADR 0007), as `role.yaml` is. A connector is `{ name, transport, … }`, `transport` one of `stdio`, `http`, `container`:
  - `stdio` and `http` take the team file's fields (`command`, `args`, `url`, `headers`, `credential_keys`, `oauth`), their definitions copied from `team.schema.json`'s `mcpServer` (typify reads one file, so no `$ref` across files), and the setup copy: `title` (the service, 1 to 60 characters), `about` (what it is, 1 to 300), `why` (why the role wants it, 1 to 300), `setup` (what the user does, 1 to 600), `key_page` (an `https` address where the key is made), required when `credential_keys` is not empty, and `labels` (optional, a tool to what it does in the user's words, 1 to 60 characters, such as `API-post-search: search pages`);
  - `container` is a server Farik runs in Docker itself: `image`, `module_root`, `args`, no copy;
  - every connector has `tools`, each tool mapped to `network`, `external_effect` or `denied` (the enum has no `read`, and a tool with no value is a schema error);
  - `allowances` maps a tool to `{ calls: 1..1000, what }`, `what` a plural noun such as "images" (1 to 40). Only step 05b reads it; this step checks it.
- **What the loader refuses**, as `KitError::Invalid` naming the field as a JSON pointer and a code: the schema's errors; `kit_role_mismatch` (`role` is not the folder's); `kit_skill_missing` (no `skills/<name>/SKILL.md`); `kit_skill_in_role` (`role.yaml` names it too; it stays in the prompt there, ADR 0011); a kit skill that `check_skill` refuses, with that refusal's code (ADR 0034's checks); `kit_connector_twice`; for `stdio` and `http`, every refusal `validate_team` gives the same entry, by running core's per-entry check on it (so a kit cannot ship a key in a header or an argument); `key_page_missing`; `label_not_a_tool` (a `labels` key not in `tools`); `package_not_pinned` (a `stdio` connector whose `command` is not `npx`, `bunx`, `uvx`, `pipx run` or an absolute path to a binary Farik ships, at `/connectors/<i>/command`; or whose first non-flag argument is not the package at an exact version, `name@1.2.3` or, for Python, `name==1.2.3`, or that carries `-p`, `--package`, `--from`, `--spec`, `--with`, `--registry` or `--index-url`, at `/connectors/<i>/args`; the review of 2026-10-02 found the first wording bypassable, ADR 0036), so the code Farik runs changes only with a Farik release and its pin review; `container_not_builtin` (a `container` whose name is not in `BUILTIN_CONNECTORS`, or a `container` in any kit but `ui_ux_designer`'s) and `image_not_pinned` (no `@sha256:`); `allowance_not_external` (an allowance for a tool not tagged `external_effect`); `copy_word_refused` (`title`, `about`, `why`, `setup`, a label or an allowance's `what` holding `mcp`, `oauth` or `token` in any case: the screens never say them), with the one exception below.
- **A service's own label may be quoted in `setup`** (the founder, 2026-10-02): "On Slack's page, copy the value labelled ‘Bot User OAuth Token’." `copy_word_refused` skips the text of a quoted label in `setup` and nowhere else. A quoted label is the text after an opening `‘` (U+2018) up to the next `’` (U+2019), after `“` (U+201C) up to the next `”` (U+201D), or after `"` (U+0022) up to the next `"`, with no line break and at most 60 characters inside. The ASCII apostrophe `'` never opens one (it is also the possessive's), an opening mark with no closing one quotes nothing, and a longer span is not a label, so its words are checked. `quoted_labels(text) -> Vec<Range<usize>>` in `kit.rs` finds them; the check runs over the text with those ranges taken out. Farik's own strings stay plain everywhere.
- **Embedding.** `load_kit(role)` embeds `kit.yaml` and each kit skill's files with `include_str!`, one match arm per role, as `load_role` does. Rejected: the `include_dir` crate (a dependency for a dozen lines) and a build script. Every role ships a `kit.yaml` from this step, with no skills and no connectors except the Designer's. `load_kit` takes the role's skill names from `load_role` and never calls `core_skill_names()`, which is built over `load_kit` and would recurse into its own initialiser.
- **Kit skills.** They live in the role's `skills/` folder beside the `role.yaml` skills, are Farik's own (neither pinned nor confirmed, as a role's are), and load on demand through step 04's plugin folder, after the agent's and the team's: one name resolves agent, team, kit (ADR 0034). Their names join the shipped names, so a team or agent skill of that name needs `replace_shipped` and then replaces it. The shipped names a command checks are `shipped_skill_names(&roles, &kits)` over the six shipped roles, with each kit taken from `ToolDeps.kits` (`io.kits` on the command line); `core_skill_names()` stays as the same set over `load_kit`, for code with no deps. `save_skill`, `confirm_skill` and `session_skills` take their kits from `deps.kits`; the CLI's two pre-checks (`cli/src/skill.rs`, the add and the confirm) use `io.kits`. `skills.list` lists a kit skill as a `role` row after the role's rows, `Replaced` when the agent's or the team's skill of that name is in use; `role_skill_get` finds `name` in the role's skills, then in `(deps.kits)(role)`'s, and answers the kit skill's `SKILL.md` as `session_files` holds it. Rejected: writing them into the prompt, which ADR 0034 keeps for `role.yaml`'s alone.
- **The built-in browser moves.** `crates/roles/connectors/playwright.yaml` becomes the `container` connector `playwright` of `roles/ui_ux_designer/kit.yaml`, every field and tag unchanged, and the `connectors/` folder is deleted. Its header comments move into `kit.yaml` above the connector: the pin's date and release, and "a tool a new pin adds goes in as `denied`". `builtin_connector(name)` keeps its signature and answers what the file answered, read from the Designer's kit, so its ten callers do not change; `source: builtin`, `BUILTIN_CONNECTORS` and `ships_every_connector_the_team_file_may_name` stay. The team file keeps `{ name: playwright, source: builtin }`, any agent may have it, and it is switched on and off as before; a `container` connector is never listed among a kit's connectable services.
- **A kit connector in the team file is written whole** (ADR 0036, Task 3): `{ name, source: kit, transport, … }` with every field from the kit and the kit's tags as its `tools`, the applied tags. Rejected: `{ name, source: kit }` resolved from the binary at each use, because every path steps 01 to 03b built (session setup, the launcher and headers helper, refresh, `team.get`, disconnect, retiring, templates) reads an entry through `custom_server`, and a whole entry keeps them unchanged. `custom_server` answers `Some` for `kit` as for `custom`, and `CustomServer` gains `kit: bool`. `validate_team` holds a kit entry to every rule of a custom one and does not know kits (`farik-core` cannot depend on `farik-roles`). `spec_sha256` adds `"source": "kit"` for a kit entry only, so every hash kept today stands and a commit that relabels `kit` as `custom` makes the server "Connect again".
- **The entry must be the kit's.** `kit_entry` builds it from the agent's role's kit. `connector_connect` refuses a `source: kit` entry for which `matches_kit` is false (`connector_not_in_kit`), which also refuses a kit's connector for an agent of another role. Session setup leaves out a kit entry `matches_kit` refuses, and `team.get` says `connect_again` for it, so a release that tags a tool `denied` takes effect at the next session. Rejected: running the stale entry until the user reconnects. The cost: after such a release the user connects that service again. `team.get` says `not_in_kit` instead for a `source: kit` entry whose agent's role's kit has no `Server` connector of its name; the row shows "Farik no longer offers this service" and "Remove" only, since "Connect again" could not work.
- **Kit trust holds on every path** (ADR 0036 records this): `connector_connect` checks `matches_kit`; session setup filters with it; the launch route (`daemon.rs::launched_server`) and the hook take only what is in the session's registration, built at setup, and re-check the kept hash (`confirmed_entry`), so the launch route needs no kit check of its own (the kit changes only with the binary, which ends every session); a team file or a clone that forges a `source: kit` entry with wider tags hashes differently from anything kept and fails `matches_kit`; a custom entry relabelled `kit`, or the reverse, changes `spec_sha256` and needs "Connect again", which `connector_connect` then refuses unless it equals the kit's.
- **Connecting lists, but writes the kit's tags.** Listing proves the key or the sign-in works; a tool the service lists and the kit does not tag is not offered (`tool_not_tagged`), and a pinned tool the service dropped costs nothing. Rejected: refusing to connect on a difference, which would lock every user out of a service that added a tool until a release. The drift test is where a difference is caught.
- **The wire.** `connectorServer` may be `{ name, source: "kit" }`, a form of its own with `additionalProperties: false`, so a browser cannot send fields the kit decides: `connector.tools`, `connector.sign_in` and `connector.connect` then build the entry with `kit_entry`, and `tags` must be `{}` (`kit_names_these` otherwise). `team.get` gains `kits` (each role on the team that has a `stdio` or `http` kit connector, with `name`, `title`, `about`, `why`, `setup`, `key_page`, `labels`, `auth` `keys` or `oauth`, and `credential_keys`), each `connectors` row gains `source`, `custom` or `kit`, and a row's state may be `not_in_kit`. No event changes: `connector.connected` records a kit's connector as it records any.
- **The command line.** `farik connect <agent> <name>` with neither `--command` nor `--url` connects the kit connector `<name>` of the agent's role, through `kit_entry(&(io.kits)(role)?, …)`. It refuses `--arg`, `--header`, `--key`, `--tag`, `--client-id`, `--callback-port`, `--scope` and `--sign-in` with it (`kit_names_these: the kit says how <name> starts, which keys it takes and what each tool may do`); reads a value for each of the kit's `credential_keys` in order from standard input, first writing `Make a key at <key_page>, then paste <KEY>:` to the error stream; and signs in, as `--sign-in` does, when the kit's entry has `oauth`. It prints the tools by tag, then where the keys or the sign-in were kept.
- **Kits are injected.** `farik_runtime::tools` defines `pub type KitSource = Arc<dyn Fn(Role) -> Result<Kit, KitError> + Send + Sync>`, and `ToolDeps` gains `kits: KitSource` (it derives nothing, so `dyn Fn` is fine): `Arc::new(farik_roles::load_kit)` wherever a `ToolDeps` is built outside a test, and a closure over a test's fixture servers in a test, which a `fn` pointer could not capture (`fixture_mcp.rs` binds `127.0.0.1:0` and writes its stdio script per test). On the command line, `CliIo` gains `pub kits: KitSource`; `CliIo::new` sets `Arc::new(farik_roles::load_kit)`, a test overrides it in `run_with`'s closure, and `project.rs::tool_deps` copies `io.kits` into `ToolDeps.kits`. `main` and `CliIo::new` are then the only places that set it outside tests. Rejected: a cargo feature (code.md has none for this), a global static (parallel tests would share it) and a fake connector in a shipped kit.
- **Pins and drift.** `pin_drift(pinned, listed)` names the tools the service added and dropped. `crates/runtime/tests/live_kit_pins.rs` runs with `FARIK_LIVE_TESTS=1` over every shipped `stdio` and `http` kit connector, with each key from `FARIK_KIT_<NAME>_<KEY>` (`<NAME>` upper-cased, `-` as `_`) or, for one with `oauth`, a bearer from `FARIK_KIT_<NAME>_BEARER`, and fails naming the connector and the variable when one is unset, and on any drift with "a pin update re-reviews every tag". No such connector ships before step 06, so its comparison is proven here by `pin_drift`'s tests and one against the fixture server. The `container` connector keeps its Docker test, now over the kit.
- **Screens.** On `AgentEdit`, "From the <role>'s kit" comes above "Added by you": each service's title and `why`, and "Connect", "Connect again", "Sign in again" or "Connected" with "Remove", or "Farik no longer offers this service" with "Remove", by `team.get`'s state. "Connect" opens `ConnectorAdd` for the kit: the `about`, `why` and `setup`, a "Get your key" link to `key_page` and one field per key, or "Sign in with <title>"; no labelling step; then "Done", which lists what the agent may do on its own (`network`), what it asks you about first (`external_effect`), and that the rest is never offered, each tool by its kit `label`, or, without one, its name with `_` and `-` read as spaces. Farik's own copy never says "MCP", "OAuth" or "token"; a service's quoted label in `setup` may.

For the founder: **O1, the mockups.** The founder approves Task 1's boards, or says to approve them automatically. Task 7 here and step 05b's screen task do not start until then; the other tasks do not depend on the boards, and Tasks 8 and 9 run before Task 7 while O1 is pending.
