## Goal

The founder's words of 2026-10-05: the Procurement Specialist "is supposed to research prices and different providers. He may request a data pipeline from the pm who can decide whether the data pipeline is necessary or whether this decision must be escalated to the owner." After this step, when a source of prices or provider data the agent lacks would change its recommendation, it asks; the Product Manager approves, declines, or escalates the request to the owner; a request whose cost is paid or unknown, or that sends the project's data out, reaches the owner unless the Product Manager declines it, and one that needs an account reaches the owner when the Product Manager escalates it; and an approved one becomes an ordinary request for the team. Under `auto` (step 10h) the Product Manager's approval is enough for a paid or unknown-cost request, never for one that sends the project's data out. Out of scope: building or connecting any candidate source (each is a later plan's, or the user's own connector); a pipeline request from any other role; the `auto` mode itself (step 10h).

## Decisions

- **A request is a record and holds no task**, as a purchase order is (10c): `farik_request_data_pipeline` records `data_pipeline.requested` and returns its number, the event's seq; the agent's task goes on with the approved sites, and asks for the source's site with `farik_request_sites` if it must read it. Rejected: holding the task until decided, which would stall research on the slowest decision in the team.
- **Its input**, checked in this order, each refusal named, nothing recorded on any: only a Procurement Specialist in the implement session of a task it is the assignee of (`in_its_own_implement_session`, `tools/sheets.rs:647`; `pipeline_refused`); `name` 1 to 100 characters on one line, `what` and `why` 20 to 600 each, with no control character in any but a line break in `what` and `why` (`pipeline_field_invalid` naming the field); `source_url` an address `site_of` accepts (`core/governor/sites.rs:91`: `https`, a named host, no user name, password or port, at most 2,000 characters), else `pipeline_url_invalid` with `site_of`'s words; `cost` `free`, `paid` or `unknown`; `needs_account` and `sends_project_data` booleans, both required (the tool's schema refuses one missing); then at most one open request of the same `name` (without regard to case) in the project (`pipeline_already_requested`), and at most 3 open requests in the project (`pipeline_limit_reached`), so a looping agent cannot flood the Product Manager. "Open", for both limits, is neither approved nor declined, an escalated request included. `source_url` may not be empty: a source with no page cannot be set up, and the owner's row shows its host. It need not be on an approved site, and approving a pipeline approves no site (ADR 0039, 2026-10-07).
- **The Product Manager's decision session** (Blocking 1). The decision is a rule in `rules::tick` (`orchestrator/rules.rs:120`), `decide_pipelines` in a new `crates/runtime/src/orchestrator/pipeline.rs`, after `budget_and_channel` and before rule 3. It runs only when `scope.task_id` is `None` and `scope.rules` is `TickRules::All`, as `review_and_retro` (`rules.rs:342`), at most one session a tick, for the oldest request not yet decided or escalated. The session is `SessionAsk { agent: <the active Product Manager>, contract: None, purpose: Verify, cwd: <project root>, executor: None, read_only: true, only_tool: Some("farik_decide_data_pipeline"), tools: None, pipeline: Some(<n>), .. }`, gated by `day_is_spent(deps, team, Role::ProductManager, ..)` (`rules.rs:656`) and `asleep` (`rules.rs:1160`). Its message, `decide_data_pipeline_message` (`orchestrator/messages.rs`), holds every field of the request in `untrusted_block` (`prompt.rs:246`; spec 8.6) and the rule below in plain words; `session.rs`'s closing instruction gains `(None, Some(DECIDE_PIPELINE_TOOL)) => PIPELINE_DECISION_INSTRUCTION` (`prompt.rs`, beside `DESIGN_DECISION_INSTRUCTION`). The session is about no task and counts against no task's sessions or cost; its dollars count against the day's (5.5). `SessionAsk` gains `pipeline: Option<u64>` (every other ask passes `None`) and `record_session_started` (`sessions.rs`) records it: `sessionStartedBody` gains an optional `pipeline`, the request's number, only on such a session, as `chat` appears only on purpose `chat`. The tick reports `TickReport::Acted { task_id: <the request's task>, what }`, `what` from `ran`; `run_until_idle` treats every report but `Idle` alike. A request's tries are its `session.started` events: when three have ended and the request is still open, the rule records `data_pipeline.escalated { pipeline, reason: "The Product Manager did not decide" }` with no agent and no session, instead of starting a fourth, and goes on to the next request in the same tick. With no active Product Manager a request waits, as a design plan does. A request whose task was `accepted` or `cancelled` meanwhile is still decided: approval files a request, which needs no open task. Rejected: copying `design.rs:164`'s `decide`, whose `contract: Some(..)` makes `spent` (`rules.rs:1129`) charge the task's sessions and cost; counting tries by the Product Manager's `verify` sessions on the task, which its review of the procurement task is too.
- **The rule that sends a request to the owner is the governor's, not the prompt's** (O6 of 2026-10-05, "the PM must escalate any process that cost money"; answer 2 of 2026-10-07, "Yes, always to me"). `farik_core::pipeline::pipeline_needs_owner(cost, sends_project_data)` is true for `paid`, for `unknown`, and whenever `sends_project_data` is true. `farik_decide_data_pipeline { pipeline, decision: approve | decline | escalate, reason }` refuses `approve` with `pipeline_needs_owner` when it is true, its sentence telling the Product Manager to decline or escalate. `needs_account` does not force it: the Product Manager's skill weighs it, and the owner sees it on an escalated request. `decline` and `escalate` are always allowed: the Product Manager may decline any request, a paid one included, without the owner (the design the founder approved on 2026-10-05). `reason` is 20 to 600 characters (`pipeline_reason_invalid`). The tool is offered only where `only_tool` names it, and refused `pipeline_decision_refused` unless the caller is a Product Manager whose `session.started`, found by `ToolContext.session_id`, names that `pipeline`; `unknown_pipeline` for a number that is no `data_pipeline.requested`; `pipeline_decided` for one approved, declined or escalated.
- **`auto`.** This step builds no mode: every request the governor holds goes to the owner unless the Product Manager declines it, and `by` is `product_manager` or `human`. Under ADR 0041's `auto` (step 10h), answer 1, "Auto may approve", lets the Product Manager approve a `paid` or `unknown` request itself, recorded `by: auto`, which still only files a request; one that sends the project's data out is refused `pipeline_needs_owner` in both modes (answer 2), and a request the Product Manager escalates, or did not decide, waits for the owner under `auto` too.
- **The owner decides an escalated request** on Today, beside the purchase orders: `data_pipeline_decide { pipeline, decision: approve | decline, note? }`, the human's alone, on `POST /command` behind the daemon's token and in the browser's RPC behind the session cookie, as `purchase_order_decide` (10c); `unknown_pipeline`; `pipeline_decided` for one approved or declined; `pipeline_not_escalated` for one open, which waits on the Product Manager; `pipeline_note_too_long` past 600 characters. The note is the owner's own words and is never wrapped (ADR 0011); the agent's fields and the Product Manager's reason are untrusted wherever they are shown.
- **Events**, four kinds, `<entity>.<past_tense_verb>`, in `event.schema.json`, spec 8.5 and every exhaustive match (`EventBody`, `kind`, `body_def_name`, `EVERY_KIND` from 87 to 91, the names of `protocol/src/lib.rs`, the fixtures): `data_pipeline.requested { name, what, source_url, why, cost, needs_account, sends_project_data }`, its seq the request's number, as `site.requested`'s, the agent, task and session on the envelope; `data_pipeline.escalated { pipeline, reason }`, the Product Manager's reason on its envelope, or Farik's sentence on none; `data_pipeline.approved { pipeline, by, reason, request }`, `request` the filed task's id (`FRK-<n>`); `data_pipeline.declined { pipeline, by, reason }`; `by` `product_manager` or `human`, `reason` the Product Manager's reason or the owner's note (`""` for none). Each of the four stays distinct under the schema's `oneOf` by its required fields and `additionalProperties: false`, as 10c's do. A decision `by: human` counts only from an envelope naming no agent and no session; one `by: product_manager` only from that request's decision session.
- **No migration** (Blocking 2). `crates/store/src/pipelines.rs`'s `data_pipelines(log) -> Result<Vec<PipelineRecord>, StoreError>` folds the four kinds and the `session.started` events naming a pipeline in seq order through the kind index (`EventQuery { kinds, .. }`), as 10c's `purchase_orders`; the first decision the request's state takes counts. `task_projections` and `waiting_on_human` (`projections.rs:450`, whose `open_*` columns hold a task) do not change. Rejected: an `open_pipelines` column, which would feed `waiting_on_human` and hold the task, as 10c found for orders.
- **One lock**, `PIPELINES` (`crates/runtime/src/procurement.rs`, beside `ORDERS`), held from the first read to the record by the request, by every decision, the Product Manager's and the owner's, and by the escalation after three tries. ### Task 1: The rule, the events and the ask

- `the_owner_decides_what_costs_money_or_sends_data` (core): `pipeline_needs_owner` is false for `(Free, false)` and true for `(Paid, false)`, `(Unknown, false)` and `(Free, true)`. RED: no `farik_core::pipeline`.
- `round_trips_every_pipeline_event` (protocol): each of the four kinds, and a `session.started` naming a `pipeline`, validates against the schema and reads back equal; `EVERY_KIND` counts 91; a `requested` carrying `pipeline`, an `approved` without `request`, a `declined` with one, and `by: auto` are refused. RED: no such kinds.
