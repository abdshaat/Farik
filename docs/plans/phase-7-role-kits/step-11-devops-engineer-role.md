## Goal

A user can add a DevOps Engineer to the team: an optional role, offered in setup's "More roles" list (as Lena) and on the Team page, not suggested, with its own picture (the brand's `extra-3` character, as `devops-engineer`) and colour. It loads with its prompt and its skill, holds the Developer's tiers and `network`, changes code (its tasks work on `feature/` or `fix/` branches), gains `git_remote` when the team lets agents push, and is reviewed by the Architect, or by a Developer when the team has no Architect. Every prompt, skill and sentence that says who changes code names it. The founder approves the mockups of every DevOps screen of steps 11 to 11f before any of their code, and ADR 0045 records the decisions those steps share. Out of scope: deploys (11b); the watch (11c); incidents (11d, 11e); the pages (11f); the kit (12).

### Task 1: ADR 0045

Opus writes it (ADR 0032), from `0000-template.md`: `docs/decisions/0045-devops-deploys-watching-and-incidents.md`, status "accepted <date>; a later step's readiness review that changes one of its decisions amends it". 0045 is the next free number at e8efb23 (0043 and 0044 are taken, and steps 10c to 10h plan none); if another ADR takes it first, this one takes the next free number and the same commit changes every reference in steps 11 to 11f, and step 12d's 0046 moves with it. Its Decision section, one paragraph each, with the rejected alternative:

1. The three tools are Farik tools of the `external_effect` tier, which the DevOps Engineer holds from step 11b; the hook is their gate: a sprint's or an incident's pre-approval, then a grant of step 02, then the approval mode on `auto` (ADR 0041, as step 10h builds it), then the ask; `auto` never lifts an incident's step (rejected: a tier check skipped by role, a second path past `evaluate_tool_call`).
2. A platform is a `Platform` the daemon gives (`DaemonState::set_platforms`), a fake in tests; the adapters are step 12's (rejected: a cargo feature, as ADR 0036 rejected one for kits; and `ToolDeps`, which exists before the daemon whose key stores the adapters read).
3. The production settings (the platform's connection, the service, the health address, the settling minutes, the error threshold) live in this computer's log for the project, set only by the owner's command from the daemon's token or the browser's cookie, never in `team.yaml` or a template, as ADR 0041's mode is (the founder, 2026-10-07, "On this computer only"); another clone starts with none (rejected: `team.yaml` beside `preview`, which travels with the repository, spec 8.4, so a pulled commit, a stale page's save or a hand edit could re-point a deploy, a restart or a rollback at another service with no event).
4. The watch is a task of its own beside the tick loop, once a minute, starting no session, because a tick runs one session to its end (`orchestrator.rs:417`); two failing checks in a row make the service unhealthy (rejected: one, which a single network blip turns into an incident).
5. A deploy task has no branch; Farik moves it to `verifying` when it records the deploy settled healthy; acceptance integrates nothing (rejected: a session that waits out the settling period, which would spend the model's time watching).
6. One incident is open at a time. When it opens, Farik restarts the service itself at once, with no model and no session, recorded `service.restarted { by: farik }` (ADR 0027 as amended 2026-10-05); `incident` sessions then investigate, and `farik_roll_back` is pre-approved once when the restart's settling ends unhealthy; any further restart or rollback is the human's, from Today, and the agent's call is refused without asking (rejected: the session making the first restart, which waits behind a running session). Step 11d's readiness review decides whether the agent is offered `farik_restart` at all.
7. The fix is filed by the incident session, triaged by Farik, marked on `task.created`, and exempt from the sprint hold, the open sprint's membership and its budget, through step 08g's `skips_sprints`; its own budget and the day's still hold (rejected: holding a production fix behind a spent sprint).
8. The first restart waits for nothing; an incident's session waits for a running session to finish (rejected: stopping it).
9. Under the team's `push` answer the DevOps Engineer gains `git_remote`, as the Developers and the Designer do (the founder, 2026-10-07, "Yes, like Developers"); a branch it pushes may deploy through the user's own pipeline, outside the three tools, the sprint's approval and the watch, which the setup copy says (rejected: `git_remote` for the Developer and the Designer alone, the readiness review's recommendation).
